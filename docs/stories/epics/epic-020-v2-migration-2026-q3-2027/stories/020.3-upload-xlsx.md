# Story 020.3 — Upload XLSX extrato + reconciliação manual

**Story ID:** 020.3
**Epic:** epic-020-v2-migration-2026-q3-2027
**Fase do plano:** Fase 3 (Bancos avançado)
**Effort:** 5-7 dias-dev (~2 semanas calendário)
**Status:** Draft
**Owner agent:** aiox-dev (lead) + supabase-designer (RPC `extrato_upsert`)
**Sequence:** Depende de 020.2 mergeado

---

## As a

Mário (admin do condomínio Prata 2A) a fazer **upload mensal de extrato bancário** XLSX e a reconciliar movimentos com documentos no Drive

## I want

Substituir o workflow crítico "🔄 Atualizar Extrato" (sidebar footer do legacy): **drag-drop XLSX** com parse client-side, **preview** das primeiras 10 linhas + count total, **upsert chunked** (50 rows/batch) via RPC em V1, **progress bar** com relatório final (inseridos/duplicados/erros), e modal de **reconciliação manual** "Associar movimento → documento" com search + Drive upload se não existir

## So that

Mário consegue importar o extrato mensal sem voltar ao legacy. Workflow crítico (mensal, falha = atraso na facturação do condomínio) com observabilidade clara (sem black-box). Reconciliação manual permite associar movimentos sem documento a uploads novos no Drive

---

## Acceptance Criteria

### Upload XLSX

1. **AC-1** — Drag-drop em sidebar footer (mesma posição do legacy "🔄 Atualizar Extrato") — slot adicionado em 020.1.
2. **AC-2** — Parse client-side com biblioteca `xlsx` (NPM, **não CDN** — versão pinned com CVE check).
3. **AC-3** — Preview da tabela parsed: primeiras 10 linhas + count total (ex: "1056 movimentos detectados").
4. **AC-4** — Botão "Importar" envia em **chunks de 50 rows** via RPC `extrato_upsert` em V1.
5. **AC-5** — Progress bar mostra % conforme chunks vão sendo confirmados.
6. **AC-6** — Relatório final com 3 contadores: **inseridos** / **duplicados** (skip por unique constraint) / **erros** (com mensagem detalhada).
7. **AC-7** — RPC `extrato_upsert(rows jsonb)` criada em V1 schema `v2_condominios` (migration file PRIMEIRO per 019.4): valida schema da row, dedup por `(data, valor, descricao)` ou similar, retorna `{inserted: N, duplicates: N, errors: [...]}`.

### Reconciliação manual

8. **AC-8** — Modal "Associar movimento → documento" abre via botão inline na tabela Bancos.
9. **AC-9** — Search de documentos existentes (autocomplete em `v2_condominios.documentos`).
10. **AC-10** — Se documento não existe: upload directo para Drive via EF `drive-upload` (ou inline `<input type="file">` + Storage Supabase fallback) + cria row em `documentos`.
11. **AC-11** — Update `extrato_bancario.drive_url` + `extrato_bancario.documento_id` (FK).

### Smoke test Fase 3 (`V2-MIGRATION-PLAN.md §3 Fase 3`)

12. **AC-12** — Upload XLSX real do extrato de Abril 2026 → tabela parsed correcta → upsert insere movimentos novos **sem duplicar antigos**.
13. **AC-13** — Associar movimento "Easyfresh - Limpeza" a documento via modal → `drive_url` actualizado, verificável via SQL.

### Riscos identificados (`V2-MIGRATION-PLAN.md §3 Fase 3 Riscos`)

- **R7**: XLSX library tem CVE histórico (Prototype Pollution). Mitigação: pin a versão patched + audit `pnpm audit`.
- **R8**: Chunks RPC podem timeout em ficheiros grandes (5000+ linhas). Mitigação: client-side throttle 1s/chunk + retry com backoff.

### Decisões a tomar

- Parse client-side ou server-side? — Client (UX faster preview, server só recebe JSON pequeno).
- Dedup key: `(data, valor, descricao)` vs hash? — Provavelmente hash MD5 da row inteira (mais robusto a typos).
- Upload Drive: EF dedicada ou inline Storage? — Provavelmente Storage Supabase com bucket `documentos-extrato` (consistência V1).

## Risk & Rollback

### Risco
- **Médio** — XLSX library historicamente com CVEs; chunking pode timeout.
- Mutação real em V1 schema `v2_condominios.extrato_bancario` (insert + update).

### Rollback
- Revert merge PR → Vercel rebuild.
- RPC `extrato_upsert` fica em V1 como idempotente; pode ser dropped se necessário (`DROP FUNCTION ... CASCADE`).
- Dados inseridos durante testes em V1: DELETE WHERE created_at > '<test-timestamp>' (manual cleanup).
