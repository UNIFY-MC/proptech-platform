# Story 020.2 — Admin core: Condóminos, Fracções, Faturas, Bancos, Configurações

**Story ID:** 020.2
**Epic:** epic-020-v2-migration-2026-q3-2027
**Fase do plano:** Fase 2 (Admin core)
**Effort:** 12-15 dias-dev (~4-5 semanas calendário)
**Status:** Draft
**Owner agent:** aiox-dev (lead) + supabase-designer (RPCs admin) + vertical-builder (modais complexos)
**Sequence:** Depende de 020.1 mergeado

---

## As a

Mário (admin do condomínio Prata 2A) a fazer **workflows daily** de gestão de condóminos, fracções, faturas, banco e configurações

## I want

Paridade dos **5 workflows admin** principais do legacy: gestão CRUD de **Condóminos** (com modal multi-tab Quota/Dívidas/IBAN/Docs), **Fracções** (com permilagem + transferência), **Faturas** (com filtros + export CSV + CRUD fornecedores), **Bancos** (associar doc + sem-fatura toggle) e **Configurações** do condomínio (NIF/IBAN/morada)

## So that

Mário consegue fazer o trabalho admin diário **inteiramente na app React** (sem precisar voltar ao legacy), incluindo bulk actions (Email/WhatsApp/Imprimir), histórico de proprietários, transferência de fracção e lookup CEP CTT. Esta é a Story que torna a app "produção-ready" para a parte admin

---

## Acceptance Criteria

### Condóminos

1. **AC-1** — Tabela completa com colunas Nome / Email / Telefone / NIF / Morada Fiscal / status email / ✏ (edit).
2. **AC-2** — Modal "+ Novo Condómino" funciona: cria row em `v2_condominios.condominos` via RPC `portal_admin_create_condomino` (ou INSERT directo com RLS via iam).
3. **AC-3** — Modal "Editar Ficha" multi-tab: Quota mensal / Dívidas / IBAN / Documentos / contactos múltiplos. Save persiste em V1 schema `v2_condominios`.
4. **AC-4** — Toggle "Mostrar inativos" filtra `where active = true/false`.
5. **AC-5** — Bulk actions: selecção múltipla + botões Email (abre modal Resend chunk 50/batch) + WhatsApp (deep link `wa.me/<phone>?text=...`) + Imprimir (PDF lista via jsPDF ou backend).
6. **AC-6** — Drawer "Histórico de proprietários" por fracção, ler de `v2_condominios.historico_proprietarios`.
7. **AC-7** — Modal "Transferir Fracção" (mudança de proprietário com data + INSERT em historico_proprietarios + UPDATE fracoes.proprietario_id).
8. **AC-8** — Lookup CEP CTT via RPC `portal_lookup_codpostal` portada para V1.

### Fracções

9. **AC-9** — Tabela com permilagem total (rodapé soma = 1000).
10. **AC-10** — Botão "+ Novo / Transferir" (abre modal de criação OU transferência).

### Faturas (admin)

11. **AC-11** — Modal "+ Lançar Fatura" (fornecedor / valor / data / nº / rubrica).
12. **AC-12** — CRUD Fornecedores standalone (página `/fornecedores`).
13. **AC-13** — Filtros funcionais: estado, fornecedor, ano, rubrica.
14. **AC-14** — Export CSV com mesmas colunas/order que legacy (`V2-INVENTORY-COMPLETE-2026-05-24.md` referencia).

### Bancos

15. **AC-15** — Botão inline "Associar documento" por movimento abre modal upload Drive + UPDATE `extrato_bancario.drive_url`.
16. **AC-16** — Toggle "sem fatura" por movimento (flag `extrato_bancario.sem_fatura_flag`).

### Configurações

17. **AC-17** — Página `/configuracoes` (admin only via `iam.has_permission('v2.configuracoes', 'edit')`).
18. **AC-18** — Campos: NIF, IBAN, código postal, morada, contactos admin.
19. **AC-19** — Save em `v2_condominios.configuracoes` (1 row por condomínio) OU `condominios.config_jsonb` (decisão durante implementação).

### Smoke test Fase 2 (`V2-MIGRATION-PLAN.md §3 Fase 2`)

20. **AC-20** — Criar novo condómino fictício "Test 2026" via modal → aparece na lista.
21. **AC-21** — Editar contactos do "Test 2026" → save → re-fetch confirma persistência.
22. **AC-22** — Transferir fracção 12-A1A para "Test 2026" → histórico mostra a transferência.
23. **AC-23** — Lançar fatura fictícia + marcar paga + confirmar log em `email_log` (se trigger email activo).
24. **AC-24** — Export CSV faturas: colunas/order = legacy.
25. **AC-25** — Configurações: alterar IBAN simulado → save → recarregar → persistiu.

## Dev Notes

### Ficheiros a tocar (`V2-MIGRATION-PLAN.md §3 Fase 2`)

- **9 views**: 4 refactor (Condominos, Fracoes, Faturas, Bancos) + 3 novas (Configuracoes, Fornecedores, HistoricoProprietarios)
- **5 components**: CondominoModal, FaturaModal, TransferirFracaoModal, BulkActionsBar, LookupCEPInput
- **App.jsx**: 2 routes novas
- **Sidebar.jsx**: 2 items novos
- **Backend separado**: 7-8 RPCs em `v2_condominios.*` (migration file primeiro per 019.4)

### Riscos identificados (`V2-MIGRATION-PLAN.md §3 Fase 2 Riscos`)

- **R4**: Migração de dados de configuração legacy → V1 pode falhar (NIF/IBAN críticos). Mitigação: dump V2 antes + diff manual.
- **R5**: Bulk actions (mass email) pode disparar Resend rate-limit. Mitigação: chunking 50/batch + delay 1s.
- **R6**: Modal Edit Condómino é o componente mais complexo (multi-tab + multi-CRUD). Risco regressão visual vs legacy. Mitigação: side-by-side screenshot comparison.

### Decisões a tomar durante implementação

- Configurações: tabela dedicada (`configuracoes`) ou JSONB em `condominios.config_jsonb`? — recomendação: tabela dedicada (queries mais simples, melhor para audit).
- Histórico proprietários: drawer dentro de Fracoes.jsx ou view separada? — recomendação: drawer (UX legacy).
- CEP lookup: RPC server-side ou client API CTT direto? — RPC server-side (cache + rate-limit).

## Risk & Rollback

### Risco
- **Médio-Alto** — toca 9 views + 7-8 RPCs novas em V1. Risco regressão visual.
- Dados V2 configuração têm que ser migrados manualmente (NIF/IBAN críticos para AT compliance).

### Rollback
- Revert merge PR → Vercel rebuild automático.
- RPCs em V1 deixadas activas (idempotent) — não removem dados.
- V2 produção intocada (Regra D4) — utilizadores continuam a usar legacy via `prataowners.pt`/Netlify durante Stories 020.1–020.6.
