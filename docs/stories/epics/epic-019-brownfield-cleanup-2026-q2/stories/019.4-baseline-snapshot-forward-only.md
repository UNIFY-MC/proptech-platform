# Story 019.4 — Baseline snapshot V1 + processo forward-only migrations

**Story ID:** 019.4
**Epic:** epic-019-brownfield-cleanup-2026-q2
**Covers debts:** DB-003 (Critical)
**Effort:** XL
**Sequence:** Fase B
**Status:** Draft

## As a

Mário e agentes que aplicam migrations (supabase-designer, data-engineer)

## I want

Estabelecer um baseline snapshot do schema actual de V1 em git, reconciliar ficheiros locais com naming divergente e instituir o processo "ficheiro local PRIMEIRO, `apply_migration` DEPOIS"

## So that

O gap de 215 migrations aplicadas via MCP sem ficheiro pare de crescer; o schema de V1 seja reproduzível a partir do git; debugging de migrations deixe de ser cego; risco de re-aplicação dupla em `supabase db push` desapareça.

## Acceptance Criteria

1. **AC-1** — Snapshot baseline `supabase/migrations/00000000000000_baseline_2026_05_v1.sql` criado via `pg_dump --schema-only` do V1 Core Hub.
2. **AC-2** — Snapshot marcado como baseline em `supabase_migrations.schema_migrations` (sem re-aplicar) via procedimento documentado.
3. **AC-3** — Os 5 ficheiros locais com naming divergente (ex: `20260513_iam_schema.sql` vs remote `20260512162753`) são renomeados para corresponder ao timestamp remoto OU marcados como already-applied em `supabase_migrations`.
4. **AC-4** — Documento `docs/database/migration-process.md` criado com regra forward-only e procedimento canónico:
   1. Criar ficheiro `.sql` em `supabase/migrations/{timestamp}_{slug}.sql`
   2. Aplicar via `apply_migration` MCP (que regista em `supabase_migrations`)
   3. Commit do ficheiro
   - **NUNCA** aplicar antes de ter ficheiro em git
5. **AC-5** — Linha de defesa: pre-commit hook ou check em `pre-push-checklist` que detecta `apply_migration` sem ficheiro correspondente em `supabase/migrations/`.
6. **AC-6** — Equivalente para V2 (Supabase produção) — baseline snapshot e processo documentado. Como V2 é produção real, snapshot é read-only sem alterar `supabase_migrations` salvo aprovação Mário.
