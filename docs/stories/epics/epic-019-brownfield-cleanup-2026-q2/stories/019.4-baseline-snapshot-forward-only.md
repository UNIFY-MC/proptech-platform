## Problem

A pasta `supabase/migrations/` tem **45 ficheiros locais** (nomeados `YYYYMMDD_…sql`) mas o registo remoto `supabase_migrations.schema_migrations` em V1 (`hkmvszkpxjbxmnixzqbl`) tem **215+ migrations aplicadas** (DB-AUDIT 2026-05-05).

Sintomas:
- `supabase db push` falha porque tenta re-aplicar migrations que já existem (versões duplicadas).
- `supabase db pull` quer importar 215 ficheiros remotos, esmagando o histórico local cuidadosamente curado.
- Naming local (`20260504_…`) **não corresponde** ao formato Supabase standard (`YYYYMMDDHHMMSS_…`, 14 dígitos) → nenhum ficheiro local é reconhecido pelo registo remoto pelo simples nome.
- Mudanças aplicadas via SQL Editor / MCP `apply_migration` desde 2026-04-12 não têm ficheiro local correspondente (drift permanente).

## Decisão arquitectural (Phase 5 review)

**NÃO** usar `supabase db dump` monolítico para reconstruir tudo. Em vez disso:

1. **Congelar o passado** num único ficheiro **baseline** schema-only (snapshot da realidade actual).
2. Marcar esse baseline como **already-applied** em `supabase_migrations.schema_migrations` (sem o executar).
3. Reconciliar os 45 ficheiros locais com o registo remoto — renomear quando possível, marcar como already-applied quando o conteúdo já está no baseline.
4. **A partir do baseline, forward-only** — toda a nova mudança vive num ficheiro `supabase/migrations/YYYYMMDDHHMMSS_descricao.sql` aplicado via `supabase db push`.

Vantagens:
- Zero risco de re-execução destrutiva (CREATE EXTENSION twice, GRANT idempotente, etc).
- Histórico local volta a ser autoridade canónica.
- Drift a partir de hoje detectável (script de check no AC-5).

## Dev Notes

### Por que `00000000000000_` como prefixo do baseline?

Supabase aplica migrations por ordem lexicográfica do nome. `00000000000000` garante que o baseline aparece **antes** de qualquer migration real (que começa com data 2026+). Em conjunto com a INSERT em `schema_migrations`, o Supabase trata-o como "já aplicado" e nunca tenta executá-lo. Convenção alinhada com `supabase/migrations-baseline` patterns na comunidade.

### Por que `pre-push-checklist.md` em vez de hook automatizado?

Considerei dois caminhos:

1. Hook `.claude/hooks/check-migration-drift.cjs` que corre em pre-commit → bloqueia commits com `apply_migration` calls sem `.sql`.
2. Documento `docs/database/pre-push-checklist.md` que Mário consulta antes de push.

Escolhi **2** porque:
- O drift acontece tipicamente em sessões de exploração no SQL Editor / MCP, **não** em commits. Um hook git só apanha o subconjunto que passa por commit.
- O check correcto é: para cada `apply_migration({version: X})` em logs/sessões recentes, existe `supabase/migrations/X_*.sql`? Isso requer parsing de logs de agente, fora do scope de um hook git.
- Hook automatizado pode falsos-positivos chatear sem resolver o problema de origem.
- O `pre-push-checklist.md` é leve, executável (5 minutos), e Mário pode fazer-lo antes de cada `git push` que toque em DB. Forward-only fica viável.

O `scripts/db/check-migration-drift.ps1` automatiza a parte do check — chamada manual quando se desconfia, não bloqueante.

### Risco e mitigação

| Risco | Mitigação |
|-------|-----------|
| Mário corre baseline-dump em V2 sem querer | Script V2 começa com `confirm: "Sim, snapshot read-only V2"` |
| Re-execução acidental do baseline | INSERT em `schema_migrations` antes de qualquer push novo |
| Drift continua após esta story | `check-migration-drift.ps1` corrido em sprints |
| Naming de 14 dígitos esquecido | Documento `migration-process.md` é canónico; review obrigatório |
