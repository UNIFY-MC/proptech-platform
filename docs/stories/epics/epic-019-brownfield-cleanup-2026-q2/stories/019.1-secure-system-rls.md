# Story 019.1 — RLS coverage em V1 + reduzir multiple permissive policies

**Story ID:** 019.1
**Epic:** epic-019-brownfield-cleanup-2026-q2
**Covers debts:** DB-001 (Critical), DB-013 (High), DB-015 (High)
**Effort:** XL
**Sequence:** Fase B
**Status:** Draft

## As a

Mário (operador da plataforma PropTech sujeita a RGPD)

## I want

Activar RLS em todas as tabelas V1 actualmente expostas via `anon_key` e corrigir performance/segurança das policies existentes

## So that

Dados operacionais e de configuração deixem de estar acessíveis via REST público; queries com RLS deixem de degradar linearmente com volume de dados; superfície de policies fica auditável.

## Acceptance Criteria

1. **AC-1** — As 14 tabelas V1 actualmente sem RLS têm RLS activo. Para `system.*` (motor agentic) sem policies explícitas — service_role bypass garante operação. Para `public.file_deploy` e `public.frequency_templates`, policies explícitas conforme estratégia documentada.
2. **AC-2** — Tabelas `*_backup_*` são dropadas (não recebem RLS) via migration formal.
3. **AC-3** — Edge Functions auditadas — zero hits de `supabase.from('system.')` sem `serviceRoleKey`. Lista de auditoria em commit.
4. **AC-4** — 38 policies V1 com `auth.<function>()` migradas para `(select auth.<function>())` (fix `auth_rls_initplan`).
5. **AC-5** — 149 `multiple_permissive_policies` em V1 reduzidas para <30 (consolidar ou eliminar duplicados/`always_true`).
6. **AC-6** — Smoke test em Preview: chamada REST com `anon_key` a cada tabela retornada do diagnóstico não devolve dados não autorizados.
7. **AC-7** — Linter `pg_catalog` advisors confirma 0 `tables_without_rls` em V1 + redução documentada de `auth_rls_initplan` e `multiple_permissive_policies`.
