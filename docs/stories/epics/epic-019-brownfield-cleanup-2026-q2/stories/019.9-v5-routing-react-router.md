Que `apps/v5-manutencao` use React Router v6 (à imagem de dashboard e v2-condominios), substituindo o routing state-based actual (`useState`)

## Dev Notes

### Estratégia adoptada: state→URL bridge, não rewrite completo

V5 tem uma restrição arquitectural canónica em `apps/v5-manutencao/CLAUDE.md`:

> **Single-file App.jsx** — `src/App.jsx` contém toda a lógica (>11.000 linhas). Isto é intencional para facilitar leitura contextual; **não refactorizar para múltiplos ficheiros sem pedido explícito**.

App.jsx tem 11.238 linhas com state machine complexo (`tab` + `ecra` + `selNav` + `catScreen` + `casaSub` + `role` + `authScreen`) e centenas de callsites de `setTab(...)` / `setEcra(...)` espalhados pelos screens via callbacks (`onNavigateServico`, `onBack`, `onAvatarClick`, etc.).

Uma migração "pura" para `<Routes>` + `useNavigate()` exigiria refactor de ~500 callsites — risco altíssimo numa app live, e em conflito directo com a regra single-file.

**Decisão de design:** introduzir React Router como uma camada de bridge sobre o state machine existente, em vez de o substituir. Concretamente:

1. **`BrowserRouter`** envolve toda a app em `src/main.jsx`
2. **`<Routes>` + `<Route>`** são usados em três locais:
   - `AuthRouter` — auth screens viraram routes URL-based (`/auth/login`, `/auth/signup`, etc.)
   - Gate de onboarding — `<Route path="/auth/onboarding">` quando `needsOnboarding=true`
   - Fallback `/404` — `NotFoundScreen` inline
3. **URL ↔ state bridge** (dois `useEffect`):
   - **URL → state**: lê `location.pathname`, mapeia para `(tab, ecra, sel)`. Garante que browser back e deep links actualizam o UI.
   - **state → URL**: quando `tab`/`ecra`/`sel.id` mudam internamente (via `setTab`/`setEcra` em handlers existentes), espelha no URL via `navigate()`. Garante que URLs ficam sincronizadas sem refactorizar callsites.
4. **Mapping tables** (`URL_TO_STATE`, `stateToUrl`) — fonte única de verdade entre URL canónica e estado interno.

### Trade-off explícito

| Pro | Contra |
|-----|--------|
| Risco baixo numa app live (zero refactor de callsites) | AC-1 "state-based navigation removido" cumprido só em parte — o state machine ainda existe internamente |
| Browser back, deep links e URL share funcionam (ACs 5/6) | Source code ainda parece state-based; programadores novos podem confundir-se |
| Respeita a regra single-file de V5 CLAUDE.md | Sub-fluxos catScreen/casaSub não têm URLs próprias (AC-4 permite isto) |
| Permite migrar gradualmente cada handler para `navigate()` directo no futuro | Bridge tem 2 efeitos sincronizados — preciso de cuidado com loops (mitigado com `_syncingRef`) |

### Convenção modais vs routes (AC-4)

Documentada em `apps/v5-manutencao/CLAUDE.md` secção "Convenção de routing (Story 019.9)":

- **Sheets/Drawers UI in-place** → NÃO viram routes (PerfilSheet, PerfilDrawer, ImovelSelectorSheet, OrgLocBottomSheet, FabPickerModal, SubscricaoScreen)
- **Wizards multi-step in-flow** → mantêm-se in-state (catScreen wizard, casaSub) — alinhado com [[feedback_config_flows_full_page]] na vertente "in-flow" (não config flows independentes)
- **Config flows independentes** → futuras (ex: `/ordens/:id/editar`) → viram routes próprias quando criadas

### Auth (AC-3)

Não migrado para `@proptech/auth` nesta story — continua a usar `./lib/AuthContext.jsx` local. Esta migração é scope de Story 019.7 (auth centralizada). O estado de sessão é preservado via `useAuth()` do AuthContext local, e o role (`cliente`/`prestador`/`admin`/`gestor`) é preservado em `useState` no App.jsx.

### Browser back e deep linking (AC-5/AC-6) — manual smoke test plan

Como não há infra de testes RTL ainda (019.8 não implementada), AC-5 e AC-6 são validados manualmente em Preview Vercel após push. Plan:

**AC-5 — Browser back (navegar 3 níveis e regressar):**
1. Login → `/` (home)
2. Click "Serviços" tab → URL fica `/catalogo`
3. Click numa categoria → URL fica `/e/categoria_detail`
4. Click num serviço → URL fica `/e/servico_detail`
5. Browser back × 3 → deve voltar a `/e/categoria_detail`, depois `/catalogo`, depois `/`, e o UI deve actualizar a cada step

**AC-6 — Deep link (copiar URL e abrir em novo separador):**
1. Em sessão activa, abrir `/ordens` e clicar numa ordem específica → URL fica `/ordens/<uuid>`
2. Copiar URL
3. Abrir em separador novo (ou sessão privada) — fluxo:
   - Se não autenticado: redirige para `/auth/login`, após login deve aterrar em `/ordens/<uuid>`
   - Se autenticado: aterra directamente em `/ordens/<uuid>` e renderiza COrdem com `sel` correcto

**Smoke routes adicionais a validar manualmente:**
- `/` → IniciaScreen renderiza
- `/catalogo` → ServicosScreen renderiza
- `/ordens` → PedidosScreen renderiza
- `/casa` → CasaScreen renderiza
- `/perfil` → CPerfil renderiza
- `/missoes` → MissoesScreen renderiza
- `/auth/login` (sem auth) → LoginScreen renderiza
- `/qualquer-coisa-que-nao-existe` → redirige para `/404` e mostra NotFoundScreen
- `/404` → NotFoundScreen renderiza com botão "Voltar ao início"
