# Story 019.2 — Verificar e corrigir exposição PostgREST de schemas custom

**Story ID:** 019.2
**Epic:** epic-019-brownfield-cleanup-2026-q2
**Covers debts:** DB-016 (Medium), DB-018 (Medium)
**Effort:** S
**Sequence:** Fase A
**Status:** Draft

## As a

Mário (operador) e qualquer agente que dependa de RPCs ou queries REST cross-schema

## I want

Confirmar — e corrigir, se necessário — que os schemas `iam`, `marketing`, `v2_new` (e `growth` se aplicável) estão expostos via PostgREST no V1 Core Hub

## So that

RPCs como `iam.has_permission()`, `iam.get_my_permissions()`, `iam.portal_token_login()` funcionem via REST para frontend; falhas silenciosas tipo `PGRST106 Invalid schema` ou retornos 404 deixem de mascarar bugs cross-vertical; tabelas de referência sem PII (ex: `core.codigos_postais`) sejam consultáveis por `authenticated`.

## Acceptance Criteria

1. **AC-1** — Diagnóstico read-only executado em V1:
   ```sql
   SELECT rolconfig FROM pg_roles WHERE rolname = 'authenticator';
   ```
   Resultado documentado no commit.
2. **AC-2** — Se `pgrst.db_schemas` não contém `iam`, `marketing`, `v2_new`, é executado o procedimento canónico do ADR-V2-002:
   ```sql
   ALTER ROLE authenticator SET pgrst.db_schemas =
     'public, graphql_public, core, system, iam, marketing, v2_condominios,
      v3_seguros, v4_energia, v5_manutencao, v1_owners_club, v2_new, growth';
   NOTIFY pgrst, 'reload config';
   ```
3. **AC-3** — Smoke test REST: chamada a `iam.get_my_permissions()` via PostgREST retorna 200 (ou 401 com JWT inválido), não 404 nem PGRST106.
4. **AC-4** — `core.codigos_postais` (205 817 rows) recebe policy de leitura pública: `CREATE POLICY codigos_postais_read ON core.codigos_postais FOR SELECT TO authenticated USING (true);`
5. **AC-5** — Smoke test: query a `core.codigos_postais` por código postal específico retorna >=1 row para utilizador `authenticated`.
6. **AC-6** — Documentação actualizada em CLAUDE.md secção "Exposição de schemas custom ao PostgREST" — confirmar que lista final está em git.
