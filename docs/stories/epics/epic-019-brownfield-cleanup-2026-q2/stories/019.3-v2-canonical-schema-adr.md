# Story 019.3 — Decidir schema canónico V2 (`v2_condominios` vs `v2_new`) e formalizar em ADR

**Story ID:** 019.3
**Epic:** epic-019-brownfield-cleanup-2026-q2
**Covers debts:** ARCH-001 (Critical)
**Effort:** M (decisão) + L (implementação)
**Sequence:** Fase A (decisão) → Fase B (implementação)
**Status:** Draft

## As a

Mário (solo founder) e arquitectos / agentes que tocam V2

## I want

Uma decisão formal e documentada em ADR sobre qual schema é canónico para V2 — `v2_condominios` (47 tabelas, dados migrados, RLS completo, app `apps/v2-condominios/` em produção) vs `v2_new` (6 tabelas limpas com FKs para `core.*`, alimentado por `v2-legacy-bridge-cron`)

## So that

Desenvolvimento futuro de features V2 acontece num único schema; queries de negócio leem dados frescos do schema correcto; o cutover do ADR-V2-003 (fases B–F) tem direcção definida; bridge cron tem destino claro (manter, descontinuar ou inverter direcção).

## Acceptance Criteria

1. **AC-1** — ADR formal `.claude/strategy/adrs/ADR-V2-007-canonical-schema.md` criado, com:
   - Estado actual (47 vs 6 tabelas, app usa qual, bridge cron faz o quê)
   - 3 opções analisadas (manter `v2_condominios` · cutover para `v2_new` · híbrido com clareza de roles)
   - Decisão tomada com racional
   - Plano de descontinuação do schema não-canónico (ou justificação para manter ambos com roles distintos)
2. **AC-2** — `apps/v2-condominios/` confirmado a usar o schema canónico — documentado em comentário no `src/lib/supabase.js` ou equivalente.
3. **AC-3** — `v2-legacy-bridge-cron` tem decisão documentada (manter / descontinuar / inverter) e — se descontinuação — plano com data.
4. **AC-4** — CLAUDE.md root actualizado: secção V2 reflecte decisão.
5. **AC-5** — ADR-V2-003 (cutover) tem update de status — fases B–F replaneadas conforme decisão de 019.3.
6. **AC-6** — Aprovação explícita de Mário no ADR (Mário tem rubrica final em decisões V2 — produção real).
